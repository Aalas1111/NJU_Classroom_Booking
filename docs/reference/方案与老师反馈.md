# 「南大教室借用工具」方案申请

> 一句话：我们想做一个**帮老师/同学自动申请教室**的工具。核心是“登录一次，之后查询空闲教室、批量生成教室借用申请草稿，都能自动完成，不用人一趟趟去办事大厅点”。

---

## 一、先请您拍板的几个问题

这部分是**我们拿不准、需要您给方向的点**，您看完后面“我们已确认可行”的内容就能明白为什么这么问。

### 1. 最终产品形态：CLI + skill，还是 Web / 壳应用？

- 我们目前已经能跑通“直接调用学校接口查询教室、保存申请草稿”。
- 第一个能用的版本是 **CLI + skill**（命令行工具，让 AI 直接调用）。
- 问题：
  - **您更希望最终是“纯 CLI + skill，用户自己装进 AI 助手”用？**
  - 还是**后续补充 Web 网页 / 桌面壳应用**，让不熟悉命令的学生也能用？
- 如果做 Web：**是否需要买服务器架网站？** 还是用校内服务器/本地跑就行？

### 2. 教师端和学生端看到的“教室借用”界面，差别有多大？

- 我们目前是按**学生身份**去探测的：学生申请时，只能在“借用用途描述”里写想用哪个教室，**不能指定具体教室**，能不能借到由学校安排。
- 但我们注意到，老师（比如您）在办事大厅里似乎**可以直接借某个特定教室**。
- 问题：
  - 教师端和我们的学生端，**操作逻辑是不是不一样**？
  - 如果老师能直接指定教室，那是**要我们按老师身份重新做一套**，还是我们现有的“查空闲教室 + 提交申请”也能覆盖老师的需求？

### 3. 借教室这件事，到底是在学校网站里跑，还是有别的路子？

- 我们确认了：**网站里确实有“空闲教室查询”和“教室借用申请”**，而且接口是能自动调用的。
- 但我们在想：**老师平时是不是有更直接的办法？** 比如：
  - 有专门的负责老师/后台，可以**不走网站自动化**？
  - 学校有没有可能**针对我们这次任务开放专门的接口**？
- 更进一步：我们是**完全依托学校的原设计**（照它现有流程做自动化），还是说**学校能接受我们提出一套新的申请流程/界面**？
- 这个问题直接决定了：我们是“适配现有系统”，还是“和学校谈新方案”。

### 4. 关于“过统一身份认证”，老师有没有更好的办法？

- 我们现在确认：不管学生还是老师，用办事大厅功能**都必须先登录统一身份认证**。
- 我们能做的：**用户手动登录一次，我们把登录状态长期保存**，之后自动调用接口不用再登录。
- 问题：
  - 老师说有没有**更省事/更安全**的认证方式？
  - 比如：学校能不能给我们**一个长期有效的服务账号/应用令牌**？这样老师和学生都不用每次过认证。

### 5. 老师主要的使用场景，是哪种？

我们猜了两种，想确认您更偏向哪种：

- **方案 A（老师自助批量申请）**：老师手里已经有一整套**学生活动列表数据**，把数据给 Agent，Agent 批量生成教室借用申请。
- **方案 B（学生自助申请）**：做一个**网站挂到服务器**，学生自己访问、自己填信息，让 Agent 帮学生申请。

问题：
  - 您更希望是 A 还是 B？还是 A、B 都要？
  - 如果做 B，才需要考虑“买服务器架网站”的问题。

### 6. 我们社团已经有个小程序，里面存了“思维训练营”活动数据

- 我们了解到：社团小程序里**已经存了同学们“思维训练营”的活动数据**。
- 如果这些数据是**结构化的**（比如每条就是：时间、地点、人数、负责人），那我们其实**连 Agent 都不太需要**——因为 Agent 最大的作用是“把自然语言转成结构化数据”，而小程序直接就有结构化数据，**直接写脚本调用接口就能批量申请**。
- 但我们也发现：**小程序目前似乎可能没法覆盖所有的活动数据**（比如您负责的 CAC 思维训练营）。
- 问题：
  - 小程序里的活动数据，**能不能导出成结构化格式**（Excel/JSON）给到我们？
  - 如果数据分散/未录入，是不是需要先把数据整理进小程序？

## 二、我们已经做了哪些探索（证明可行）

这部分是告诉您：**不是空想，我们已经动手验证过了。**

### 1. 登录：确认“登录一次，之后免登录”

- 办事大厅的所有功能，都先跳转到**南京大学统一身份认证**。
- 我们确认：**用户扫码或密码登录一次后，我们可以把登录状态长期保存**（能做到一年级别的有效期），之后调用查询、申请接口都**不再需要用户重复登录**。
- 也就是说，“第一次要用户扫一次码，之后自动跑”是可行的。

### 2. 查询空闲教室：确认能拿到实时数据

- 我们已经在学校“空闲教室查询”页面后端的接口上，跑通了一次真实查询。
- 示例：查询仙林校区某栋教学楼，某天某个时段，**能返回符合条件的教室列表**，包括教室名称、容量、第几节课是否被占用。
- 所以“自动查空教室”是**已验证可行**的。

### 3. 教室借用申请：确认能“保存草稿”

- 我们在“教室借用申请”页面下，确认了**“保存为草稿”**这个功能。
- 并且**用测试数据真实保存了一条草稿**（没有正式提交，不进入审批流程）。
- 保存后，这条草稿能在申请列表里看到；之后我们也把它**成功删除了**，没有留下测试残留。
- 所以“自动生成申请草稿、再由老师确认后提交”是**已验证可行**的。
- 至于正式提交申请，还没测试，我怕我自动化测试提交太多次垃圾申请会被封禁（）。

### 4. 我们能拿到哪些数据（不用人工录入）

- 校区（鼓楼/浦口/仙林/苏州）
- 教学楼、教室类型、教室容量、教室每节课占用情况
- 当前学年学期、可借用日期范围
- 当前登录人的院系单位、联系电话等基础信息

### 5. 现在还没验证/有风险的点（如实说明）

- **教师端**的具体操作逻辑，我们还没用老师身份去试（因为我们手上是学生身份）。
- **扫码登录能否直接把二维码显示到我们自己应用里**（避免弹出浏览器），还没实测，但技术上可行。
- **批量申请**：我们验证了“单条保存草稿”，但“几百条一起批量申请”还没实际跑过，需要看学校系统能不能承受、会不会风控/限流。
- **是否允许正式提交**：目前我们只是“保存草稿”，不会真的提交进入审批，避免造成真实占用。

---

## 三、我们下一步想怎么做（供您参考）

在您拍板上面问题后，我们建议这样推进：

1. **先做一个最小可用版本**：登录、查空闲教室、生成申请草稿。先让老师手动确认后再正式提交。
2. **把“批量申请”做成一个工具**：老师给数据，工具自动拆分、查教室、排时间、生成草稿。
3. **等老师确认需求倾向后**，再决定要不要做网页 / 桌面壳应用 / 学生自助入口。

---

**一句话收尾**：技术上我们已经确认“能登录、能查教室、能存草稿”，现在最需要的不是继续写代码，而是**您帮我们定方向**：产品给谁用、要不要服务器、能不能拿到小程序的活动数据、老师端和学生端要不要分开做。
