# 思维过程 1 —— 从「能跑」到「值不值得做」

> 记录时间：2026-09（初步探测结束后）
> 背景：老师看完《方案申请》后回复——六个问题基本让我们自己定，唯一明确建议是**不要和小程序对接**（小程序是社团另一位同学的项目，对接麻烦）。

---

## 一、已经确定的事实

1. **技术可行**：登录态可持久化；空闲教室查询、教室借用申请（保存草稿/删除）都能直接调学校接口跑通。
2. **产品形态先做 CLI + skill（学生端）**，目标是兼容主流 AI harness、功能先跑通。
3. **不做小程序对接**：数据来源问题与本项目解耦，后续单独讨论。

---

## 二、老师的态度与我们的解读

- 六个问题（产品形态、教师端/学生端差异、是否有官方接口、统一认证、使用场景、小程序数据）**老师基本都让我们自己决定**。
- 这其实是**放权**，也意味着**没有额外资源**：拿不到官方接口、拿不到长期服务账号。
- 唯一明确建议：**别和小程序对接**。

---

## 三、效率优化的两条路

### 路 A：解决「活动列表从哪来」

- 这是**数据来源问题**，和教室申请本身关系不大，可以单独开项目。
- 效率建议（抛砖引玉）：社团小程序里已经有最大头的活动数据——「学生开办的思维训练营」。
- 但**不强制**：也可以人工整理。**注意：不与小程序对接。**

### 路 B：改用教师端入口

相比学生端：

| 维度 | 学生端 | 教师端 |
|---|---|---|
| 批量提交被风控概率 | 可能更高 | 更低（老师之前大量借过也没被封） |
| 流程长度 | 较长 | 更短 |
| 能否指定具体教室 | 只能写用途，等分配 | 更容易直接借到指定教室 |

- **代价**：需要 CAC（指导老师）在开发期提供他的统一身份认证登录凭证；后续维护可能还需要他时不时提供。
- **本质**：这是一个**信任问题**，不是技术问题。

---

## 四、核心困境（必须想清楚）

如果产品定位是「分发给每个社团成员，让每个人自己用 agent 申请空闲教室」：

- **若仍是学生端**：agent 的价值≈「帮用户打开网站，把自然语言填进表单」。
  - 节省的效率极低；
  - 用 AI 还要花 token；
  - 用户甚至没减少输入量——自己填表省下的字，还得写成自然语言喂给 AI。
- **若能拿到 CAC 的登录凭证**：相当于让社团所有人获得「教师端申请权限」，价值明显提升。

**结论：**
- 学生端 agent 单独存在的价值有限，**真正的效率来自「批量」和「教师端权限」**。
- 所以项目成败更取决于：**能不能形成批量场景 + 能不能拿到教师端凭证**，而不是代码写得多好。
- Web / 壳应用**对效率提升不明显**，暂不做。

---

## 五、当前决策

1. **先做学生端 CLI + skill**，把「登录 / 查空闲教室 / 批量存草稿 / 查询 / 删除」跑通并打磨成稳定工具。
2. **同步筹备教师端**：等 CAC 明确是否愿意提供凭证，再决定是否开发教师端入口。
3. **数据来源**与「是否教师端」作为独立议题推进，不阻塞 CLI。
4. Web / 壳应用**暂缓**。

---
