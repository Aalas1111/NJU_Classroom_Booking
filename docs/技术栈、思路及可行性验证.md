# 技术栈、思路及可行性验证

> 项目：南京大学教室借用自动化工具，CLI + Skill
> 起草：李赫 · 2026-09-13

一句话：做一个「用户登录一次之后，自动查空闲教室、批量生成教室借用申请」的工具。
目前学生端的 CLI + Skill 初版已经跑通，下面说明技术栈、整体思路，以及已经验证到哪一步。

---

## 一、背景：我们请教老师的六个问题

1. 最终产品是纯 CLI + Skill、用户自己装进 agent 用，还是后续补充 web 或壳应用？如果要补充，补充什么，需不需要买个服务器架网站？
2. 教师登录办事大厅看到的教室借用界面，和学生端有哪些不同？我记得 CAC 似乎可以直接借某个特定的教室，而学生端的申请界面只能在简介里写想要哪间教室，还不一定借得到。
3. 借教室这套逻辑是在网站里跑，还是老师有专门的路子，可以不通过网站就拿到自动化能力？学校能不能针对这件事专门给我们开放一个接口？我们是完全依托学校的原设计，还是能让学校接受我们的新设计？
4. 过统一身份认证这件事，老师有没有更好的方法？
5. 老师使用这个 agent 的主要场景，是手里已经有一整套学生活动列表数据、让 agent 完成批量申请；还是要设计一个网站挂到服务器上，让学生访问网站、自己让 agent 申请？
6. 我们社团已经有个小程序，里面存了所有人的「思维训练营」活动数据。有了这个数据就能直接传给 agent 完成批量上传，甚至 agent 都不需要，因为 agent 主要负责「自然语言转结构化数据」，直接上脚本就行。但我也发现，小程序目前似乎还没有包含 CAC 的思维训练营活动。

## 二、老师的反馈

几个问题基本全是让我们自己想。唯一明确的建议是：**最好别和小程序对接，可能比较麻烦**。

---

## 三、思路

### 3.1 效率到底从哪里来

目前的思路是先把学生端的 CLI + Skill 搞定。后续如果还需要继续优化效率，也就两条路。

**第一条路：把整个社团需要申请教室的活动列表拿到手。**
这个信息来源到底怎么搞，其实和我们这个项目关系不大。要么有人手动整理，要么完全可以单独开一个新项目去思考。这里可以抛砖引玉给一个效率优化建议：小程序里已经有最大头的活动数据，也就是「学生开办的思维训练营」。

**第二条路：走教师端的教室借用入口。**
相比学生端，批量发出申请时更不容易被封号，流程更短，也更容易借到指定教室。不过就算真的存在检测，CAC 之前就借过很多教室，也没人封他，我估计学生端应该也不至于封。代价是需要 CAC 在开发时给我提供他的统一身份认证登录凭证，后续项目维护可能也需要他时不时提供。

**web 和壳应用目前不觉得对效率有很大提升。**

有一点必须明确：如果这个项目最后做成「分发给各个社团成员，让每个成员自行使用 agent 申请空闲教室」，那它对效率的提升应该是微乎其微的。走学生端的话，这个 agent 的作用就等同于帮用户打开网站，再把用户输入的自然语言填进表单。我认为这样省出来的效率很低，而且用 AI 是要花 token 的，用户甚至几乎减少不了输入的字数：本来自己填表省下来的字数，还得把自己的需求写成自然语言喂给 AI。

如果能拿到 CAC 的登录凭证，那还算有点作用，相当于让社团所有人都有了教师端申请的权限。但真正的效率提升在于**统一批量处理**：只要拿到所有活动的数据，就能一键完成所有人的申请，并且可以保证申请不存在时间和教室上的冲突。

### 3.2 一个绕不开的冲突问题

对于学生端来说，南大系统从未保证一定能分配到某个教室。这就引出一个问题：如果一间空教室已经被一个学生在备注里要求分配，在这个申请被审核通过之前，这间教室还能不能被其他人申请？如果一间空教室被两个人同时申请，学校会如何处理？我猜应该就是找另一间满足条件的空教室分配给其中一个人。

也就是说，让社团里的每个人自行申请空教室，很容易导致冲突，申请的教室不一定是最终分配到的教室。反过来看，有更高的概率申请到特定的教室，这本身就是统一申请的优势之一。

### 3.3 为什么初版本做 CLI + Skill

现在 agent 基本都依靠终端敲命令来调用各类工具，命令行工具加 Skill 的模式比较常见。对已经搭建好个人 agent 的用户来说，可以比较轻松地即插即用。如果需要照顾小白用户，搭建网页和做成应用是更好的选择，能避免安装和搭建环境的困难。考虑到用户群体是社团内部使用，我觉得初版本做成 CLI + Skill 是可以的。

### 3.4 为什么选择网页自动化

我其实没借过教室，只知道南大 app 和电脑网页上的网上办事大厅可以申请。手机 app 比较难用 AI 自动化，所以只能走网页；而且网页自动化的途径和可参考经验也比较多。

### 3.5 落地过程

关于教室借用，我只知道南大 app 和电脑网页上的网上办事大厅能办，第一想法就是逆向分析这几个网页，然后做网站自动化。

具体过程是把空闲教室和教室借用这两个网址都发给 AI，让它自己访问、分析网页后端，把需要的后端接口都提取出来，包装成 CLI 工具，再写 Skill 教 AI 怎么用 CLI 工具。思路很明确。

但是让 AI 访问网址之后就发现了一个问题：AI 没法过统一身份认证，只能让我扫码。这咋办呢。我也不知道，就在 AMA 群里搜了一下，发现有群友发了一个和统一认证有关的 GitHub 项目，[NJUAlwaysLogin](https://github.com/lyc8503/NJUUtils/blob/main/NJUAlwaysLogin.user.js)，我就把这个项目扔给 AI 分析了，AI 分析之后说，这个项目能让登录凭证持续一年左右。

那行吧。这就导致我们做出来的 CLI 工具，必须由用户手动登录一次才能后续正常使用，不知道有没有更好的办法。然后 AI 就把 CLI + Skill 开发完了。

## 四、技术栈

| 层面 | 选型 | 为什么这么选 |
|---|---|---|
| 语言 | Python 3.12 | 生态成熟，写接口调用和数据处理快 |
| 环境与打包 | uv | 一个工具管依赖、虚拟环境和构建，用户装起来不用折腾 |
| 命令行框架 | typer + rich | 类型友好，`--help` 和表格输出直接可用 |
| 网络请求 | httpx | 直连学校后端接口，登录态用 Cookie 复用 |
| 数据结构 | pydantic | 学校接口字段命名混乱，统一做别名映射和校验 |
| 登录 | Playwright | 驱动一次有头浏览器让用户自己完成统一认证，我们不接触密码 |
| 交付形态 | CLI + Skill | 命令给 AI 调用，`SKILL.md` 告诉 AI 什么时候用、怎么用 |
| 质量 | pytest + ruff + GitHub Actions | 24 个单元测试离线可跑，静态检查和 CI 自动化 |

**协同方式**：CLI 负责「怎么调接口」，Skill 负责「什么时候调、参数怎么填」。所有命令都支持 `--json`，方便 AI 直接读结构化结果，不用解析人类可读的表格。

## 五、可行性验证

### 5.1 已经验证过的

| 能力 | 验证结果 |
|---|---|
| 登录态持久化 | **已验证**。用户扫码或输密码登录一次，认证 Cookie 持久化到本地，之后所有命令免登录；失效时会提示重新登录，不会静默失败 |
| 空闲教室查询 | **已验证**。走学校权威接口 `kxjscx/cxkxjs.do`，节次过滤由服务端完成，返回教室名称、容量和空闲时间段 |
| 申请草稿 | **已验证**。用测试数据真实保存了一条草稿，能在申请列表里看到，之后成功删除，没有留下残留 |
| 批量规划链路 | **已实现**。查空闲教室 → 按活动人数过滤容量 → 批次内与跨批次冲突检测 → 自动分配教室；默认只出方案，用户确认后才批量存草稿 |
| 工程与交付 | **已通过**。24 个单元测试和 ruff 静态检查全绿，CI 在 Windows 和 Linux 上自动运行，已构建并发布 v0.0.0 的 wheel 与源码包 |

这套工具现在能拿到的数据，都不用人工录入：校区、教学楼、教室类型、教室容量、每节课的占用情况、当前学年学期、可借用日期范围，以及当前登录人的院系单位和联系方式。

### 5.2 还没验证、有风险的点

- **教师端的操作逻辑**：我们手上是学生身份，还没用老师身份试过。
- **二维码内嵌到应用内展示**：现在还是弹出浏览器让用户扫码。把二维码抓下来直接显示到我们应用里，技术上可行，但还没实测。
- **大批量申请**：单条草稿已经实测，批量存草稿的链路也已经写好，但几百条一起提交还没实际跑过，需要看学校系统能不能承受、会不会风控或限流。
- **正式提交**：目前一律只存草稿，不真的提交进入审批，避免在学校系统里留下垃圾数据。
- **长效登录的真实时长**：参考项目 [NJUAlwaysLogin](https://github.com/lyc8503/NJUUtils/blob/main/NJUAlwaysLogin.user.js) 的做法，是把 `CASTGC` 的过期时间重写成一年。实际能维持多久取决于学校统一认证策略，我们以命令提示失效为准，不假设它一定有一年。

### 5.3 怎么自己复现

```bash
git clone https://github.com/Aalas1111/NJU_Classroom_Booking.git
cd NJU_Classroom_Booking && uv tool install ".[login]"
crb login                                                 # 登录一次
crb free --campus 3 --date 2026-09-10 --period 1-2 --json  # 查空闲教室
crb plan --file examples/plan.example.json                # 批量规划，只出方案
```

默认只出方案、只存草稿，不会真的提交申请。

## 六、下一步，以及想请老师帮忙的地方

1. **教师端入口值不值得做。** 如果值得，需要 CAC 在开发期提供一次统一身份认证凭证；也想确认后续维护大概需要他配合到什么程度。
2. **活动数据能不能拿到。** 社团小程序里的「思维训练营」数据能否导出成结构化格式；CAC 自己的思维训练营活动目前似乎不在小程序里，这部分数据来源也需要确认。
3. **有没有可能拿到长期有效的服务账号或应用令牌。** 这样「用户手动登录一次」这个步骤就可以省掉，体验上会好很多。
4. **初版之后要不要补 web 或壳应用。** 我们的判断是暂时不做，理由是它对效率的提升不如批量处理来得直接；如果考虑到给不熟命令行的同学用，可以再排期。
